# Hermes 项目全生命周期交付标准工作流（融合小米Agent优化版）

> **归档日期**：2026-09-21  
> **核心定位**：从一个项目进门、需求对接，到架构设计、TDD 施工、独立红队验收、双平台发版及售后沉淀的全生命周期标准操作规范（Runbook）。  
> **关联技能**：`project-delivery-workflow`（主干执行）、`task-operations-manual`（工单入口与九环闭环）、`using-superpowers`、`brainstorming`、`test-driven-development`、`systematic-debugging`、`release-consistency-audit`。

---

## 一、三条红线与不可逾越的角色边界

| 角色 | 核心职责 | 绝对禁止事项 |
|---|---|---|
| **老板** | 需求发包、设计审批、计划审批、Git push/发版授权、终验拍板 | 不陷入底层编码施工细节 |
| **Hermes（小兔/督导）** | 任务定轨、开单、门禁检查、任务指派、施工督导、证据核验、沉淀归档 | 严禁替代红队做终验结论；严禁擅改白名单外文件 |
| **施工 Agent（cline 等）** | 编写代码、调整界面、执行 TDD、自测、提交结构化回执 | 严禁自己宣布“任务完成”；严禁未经授权执行 git push |

### 🚨 全程三条铁律（每个阶段准出硬卡）：
1. **凡改必单**：白名单外零顺手改；一旦发生范围膨胀（Scope Creep），必须退回 S0 修改工单。
2. **干活的不判卷**：施工方绝不能充当判卷人；必须由 Hermes 督导结合独立红队与实际物证断言。
3. **证据说话**：严禁口头汇报或口嗨“已完成”；无真实终端输出、无版本对拍、无端到端验证者一律打回。

## 二、任务分级判据（T0 – T4 严格分轨）

当任务进门时，首先进行分轨定级。若同时命中多条规则，**严格取最高档**：

| 轨型 | 典型场景信号 | 最低准入门槛与交付要求 |
|---|---|---|
| **T0 只读/问答** | 纯查文档、解释代码、只读健康巡检、不改动任何本地文件 | 无需开单，直接回答交付 |
| **T1 薄单** | 单文件改动、文案修正、轻量脚本调优、无鉴权、无生产数据风险且天然可逆 | 快速设计（可免架构图）+ ≤5 步计划 + 极简回执与验收输出 |
| **T2 标准单** | 新功能开发、中等重构、接口契约变更、多文件协作、需要编写测试 | 严格走完 S0–S6 全流程；S1 必须有可视化产物或落盘结构图 |
| **T3 重量单（B级+）** | 跨仓跨服务联动、数据持久化 Schema 变动、公网暴露、支付/鉴权/Token 机制变动、破坏性运维、长周期过夜任务 | T2 标准 + 强制独立红队审查 + 强制老板双确认（计划一次、发布一次）+ 优先选用 AO 流水线载体 |
| **T4 机制/巡检类** | 句式含“每天/定期/巡检/雷达/自动做/别再出现X”、涉及 cron 守护或 webhook | 必须先走【机制类九环闭环体检】（定义体验→闭环图→四必问→分层→回滚锚→落盘实测），再决定是否写代码 |

> **边界强制升级信号（命中即直升 T2，常直达 T3）**：
> 删除生产数据、`git push -f`、修改网关传输 Wire-format、替换底层数据库引擎、引入外部长期依赖、鉴权/安全模型变更。

## 三、全生命周期七阶段门禁（S0 – S6 执行流水线）

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ S0: 进门 │──►│ S1: 设计 │──►│ S2: 计划 │──►│ S3: 施工 │──►│ S4: 验收 │──►│ S5: 发布 │──►│ S6: 沉淀 │
│   分流   │   │  (硬闸)  │   │  选载体  │   │ TDD+回执 │   │ 红队+5件 │   │ 双仓+3源 │   │ 错题入库 │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### S0: 进门分流（Gate 0）
- **触发**：`task-operations-manual`、检索既有技能与知识库资产。
- **动作**：明确目标、约束与边界；打出 T0–T4 标签；T1+ 必须立单并锁死白名单文件；T2+ 拟定可测验收草稿（≥3条）。
- **准出**：定轨明确 + 单号与白名单锁定 + 验收项草稿。
- **打回**：需求含糊不清 → 停留在 S0 追问，绝不推进到 S1。

### S1: 设计门（Gate 1 · 核心硬闸）
- **触发**：`brainstorming`（方案、创造性、新模块前强制）。
- **动作**：
  1. 梳理“目的、约束、成功标准、非目标”四栏；
  2. 提供 2–3 种方案及利弊权衡，对标高星开源项目；
  3. 审查通用五律：Hub 轴心协议、Fail-Open 韧性、契约锁定、手术刀工具、Agent-Native；
  4. **可视化产物（缺一不可过门）**：架构类必须用 `markdown-viewer` 画图落盘；UI/Web 界面必须产出 HTML 线框稿推 preview 静态站供老板浏览器过目。
- **准出**：设计文档 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 落盘 + 可视实物 + **老板明确批准**。
- **打回**：无图、无老板批准、成功标准不可测 → 禁止写任何实现代码（牢记：功能开发 ≠ 运维排障）。

### S2: 写计划与载体路由（Gate 2）
- **触发**：`writing-plans`。
- **动作**：将设计拆分为可独立验收的最小步骤。每一步均标明：改动文件、验证指令、回滚方案、DoD 标准。
- **载体二选一（严禁双跑双审）**：
  - **AO 工作流**：能提前画成 YAML 规范图纸、需过夜/无人值守、大盘透视的重量长任务；
  - **会话内执行**：需求需边聊边改、每步需老板实时拍板的紧耦合任务。
- **准出**：计划清单可逐项打勾 + 步骤验证命令非空 + 载体唯一确定。

### S3: 施工执行（Gate 3）
- **触发**：`executing-plans` 或 `subagent-driven-development`。
- **动作**：Hermes 任督导不下场，派工 cline 等施工代理执行。
- **写码铁律**：
  - `test-driven-development`：严格遵循 RED-GREEN-REFACTOR；协议/网关类修复必须以 issue 命名编写契约锁定测试；
  - 国内开源与协作：严格遵守 `chinese-git-workflow` 与 `chinese-commit-conventions`；
  - 卡壳排障：遵循 `systematic-debugging` 建立最小红绿反馈环，网关/中间件切面严守 Phase 4.1 Fail-Open 条款；
  - 前端变更：接受 UI-GATE 巡检。
- **准出**：本步单元/集成测试全绿 + 结构化施工回执（执行命令、退出码、真实终端输出）+ 零白名单外污染。
- **打回**：范围超纲 → 退回 S0 改单；连续 2 次无新证据同态失败 → 停手呼叫督导，严禁脑补硬上。

### S4: 验收与独立红队（Gate 4 · 防假绿灯）
- **触发**：`verification-before-completion` + 独立红队子代理。
- **证据五件套规格标准**：
  1. **指纹/版本对拍**：改动前后哈希、多副本对拍一致；
  2. **原始终端输出**：保留真实执行命令与带 tail 截断的原生回显（严禁模拟/编造日志）；
  3. **反向验证**：真实演练“红（未改前失败/故障触发）→ 绿（修复后通过）”的翻转过程；
  4. **回滚锚点**：备份文件路径、上一版本镜像 ID 或 Git commit 锚点真实存在且有效；
  5. **沙盒零污染**：临时构建目录、测试 SQLite 数据、测试网络端口测完即清。
- **零报错移交门**：Web 界面必须在真实浏览器环境访问，Network 面板 `responseStatus >= 400` 完全清零。
- **准出**：验收条目全打勾 + 五件套齐备 + 红队报告无阻断项 + 老板拍板认可。
- **打回**：缺少任何一项物证 → 直接打回 S3 重新补证。

### S5: 发布落地（Gate 5）
- **触发**：`git-project-lifecycle` + `github-pr-workflow` + `release-consistency-audit`。
- **动作**：
  1. **老板亲口批准后，方可执行 git commit / git push**；
  2. 双仓双推：GitHub 主仓（iMissNan）+ Gitee 镜像（miss–you）；
  3. 发版一致性自检：严格确保 Git Tag、项目源码版本字段与 CHANGELOG.md 三源完全对齐；
  4. 部署服务：遵循 `self-hosted-app-upgrade` 与 `home-server-edge-gateway` 进行安全重启与边界收口。
- **准出**：三源一致 + 双平台 Release 成功发布 + 部署健康检查全绿。

### S6: 售后与工程沉淀（Gate 6）
- **触发**：`skill_manage` + Obsidian 知识库。
- **动作**：
  1. 施工与验收中踩过的坑，提炼成标准化规则回填到对应技能中（**教训入技能，禁止灌入记忆库水漫金山**）；
  2. 针对返工与红队拦截事件，输出结构化复盘卡入错题本；
  3. 资产主卡落库 Obsidian，遵循单例原则建立双向链接；
  4. 周期性机制需求转入 cron 定时巡检与健康看门狗。
- **准出**：复盘卡归档 + 技能卡知识更新 + Obsidian 卡片挂链对齐。

## 四、异常打回与熔断升级矩阵

当流水线遭遇阻断或异常时，遵循以下确定性流转逻辑，杜绝无限自旋：

| 故障现象 | 打回去向 | 处置要求 |
|---|---|---|
| 发现缺少测试、测试未真红、输出伪造 | **退回 S3 (施工)** | 施工方重新执行真实命令，补充原始终端输出 |
| 施工中途发现需扩展未授权的文件/接口 | **退回 S0 (进门)** | 停止修改，重写工单范围锁与白名单，老板确认后方可继续 |
| 方案设计无法落地、核心约束被打破 | **退回 S1 (设计)** | 重新展开头脑风暴，修订技术方案与架构图，重新呈批 |
| 仅发布前 Tag / CHANGELOG 版本号不匹配 | **退回 S5 (发布)** | 仅修订版本元数据，重新跑一致性审计，严禁强推 |
| **同阶段连续 2 次打回失败** | **熔断呼叫老板** | 立即停止自动化尝试，整理两次失败证据差分，报老板人工拍板裁决 |
